Lab 13 · Evidence report

APIM 로깅 성능·무손실 벤치마크

고객 관점의 결론은 단순합니다. API가 200으로 성공해도 감사 로그가 전달됐다는 뜻은 아니며, 본 관측에서는 APIM Event Hub 로거가 로그를 조용히 드롭할 수 있었습니다. 큐 한도 메커니즘은 조건부/추정이며, 공식 EventHubDroppedEvents 정의와 Capacity·RPS 상관관계로 해석했습니다.

요약

API 성공 ≠ 로그 전달

19개 클라이언트 JSON은 모두 offered == successful, errors 0이지만, E8/E64에서는 APIM EventHubDroppedEvents가 관측됐습니다.

확정 · RESULTS.md + result.json

EH namespace는 병목 아님

8KB 500 RPS는 약 4 MB/s로 40 TU의 약 10%이며, 관측 run에서 EH throttling 0이었습니다. 드롭은 APIM 쪽에서 보고됐습니다.

확정 · EXPERIMENT-LOG.md

payload가 운영 범위를 좁힘

8KB E8은 300 RPS에서 드롭 0, 400 RPS에서 2,933 드롭이었고 64KB E64는 300 RPS에서도 41,435 드롭이었습니다.

조건부 · RESULTS.md

body 로깅은 Duration 증가

A8은 metadata-only N8 대비 APIM Duration을 높였습니다. 500 RPS에서는 N8 0.10~0.35 ms, A8 0.90~2.50 ms입니다.

확정 · EXPERIMENT-LOG.md

Basic v2 차이는 조건부

Basic v2는 관측 창에서 약 30,000/min EH 도달과 클라이언트 전부 200을 보였지만, v2 CPU/memory와 드롭 메커니즘은 미수집입니다.

조건부 · RESULTS.md

첫 화면 고객 action

  1. API SLO와 로깅 SLO를 분리하십시오.
  2. APIM EH drop/success와 EH ingress/throttling을 함께 모니터링하십시오.
  3. 피크 RPS × 기록 페이로드 크기로 용량을 계획하십시오.
  4. v1은 classic Capacity, v2는 gateway CPU/memory를 권위 부하 지표로 사용하십시오.

범위 주의: 원래 계획은 조건별 3회 반복과 request ID/hash reconciliation이었으나 실행 데이터는 대부분 one run per cell이며 서버 카운터 중심입니다. N은 metadata-only 기준선이지 diagnostics disabled가 아닙니다.

가설 판정

H1 · App Insights 8KB body 비용

의도 기준: A8 평균 gateway CPU 또는 p99가 N8보다 의미 있게 높고 세 반복이 같은 방향.

실제 증거: 3회 반복은 없었지만 APIM Duration은 기록된 모든 RPS에서 N8보다 A8이 높았고 500 RPS는 0.10~0.35 ms에서 0.90~2.50 ms로 증가했습니다.

판정: 기록된 포인트에서는 body 로깅 비용 방향이 확인됩니다. 1,000 RPS 공식 경고 구간은 미검증입니다.

안전 재사용 문장: 본 Developer v1·Korea Central·8KB 관측에서는 App Insights body 로깅이 APIM Duration을 늘렸습니다.

확정 · EXPERIMENT-LOG.md / RESULTS.md

H2 · Event Hub 8KB 500 RPS 무손실

의도 기준: generated/offered ≥ 99%, 성공 RPS ≥ 495, 오류율 ≤ 1%, p99 ≤ N8의 120%, request ID와 payload hash 대조.

실제 증거: 클라이언트는 150,000/150,000 성공했지만 APIM EventHubDroppedEvents가 대량 관측됐습니다. 300 RPS 이하는 드롭 0, 400 RPS는 2,933 드롭입니다.

판정: 500 RPS 무손실은 반박. 정확한 드롭률은 미확정이며 off-scale 질적 표시만 사용합니다.

안전 재사용 문장: API 200 성공은 Event Hub 감사 로그 전달 성공을 보장하지 않습니다.

드롭/위험 · RESULTS.md

H3 · 64KB Event Hub 무손실

의도 기준: H2와 동일하되 64KB 전체 메시지와 N64 대비 p99를 확인.

실제 증거: E64는 300 RPS에서 41,435, 500 RPS에서 76,434 EventHubDroppedEvents가 관측됐고 EH throttling은 0입니다.

판정: 64KB에서는 관측 운영 범위가 8KB보다 더 좁습니다.

안전 재사용 문장: payload가 커지면 같은 RPS에서도 로그 전달 가능 범위가 급격히 줄 수 있습니다.

드롭/위험 · EXPERIMENT-LOG.md

H4 · payload 운영 범위

실제 증거: 8KB E8은 300 RPS에서 드롭 0, 400 RPS에서 2,933 드롭이었고 64KB E64는 300 RPS에서도 41,435 드롭이었습니다.

판정: 병목 판단은 RPS만이 아니라 초당 기록 bytes를 함께 봐야 합니다.

안전 재사용 문장: 피크 RPS × 기록 페이로드 크기로 APIM 로깅 용량을 계획해야 합니다.

확정 · EXPERIMENT-LOG.md

H5 · SKU 비교

실제 증거: 동일한 EH 40 TU와 load VM에서 Developer v1은 8KB 500 RPS E8 대량 드롭, Basic v2는 분당 약 30,000 EH 도달과 클라이언트 150,000 전부 200을 보였습니다.

판정: SKU에 따른 결과 차이는 관측됐지만 v2 CPU/memory가 없어 메커니즘은 조건부입니다.

안전 재사용 문장: 모든 로그 감사가 필요하면 목표 부하에서 게이트웨이 SKU와 권위 지표를 직접 검증해야 합니다.

조건부 · EXPERIMENT-LOG.md

교정된 표현

거부할 표현: Event Hub가 항상 App Insights보다 빠르다. Developer v1의 최대 처리량은 500 RPS다.

교정된 문장: Event Hub가 항상 App Insights보다 빠르다고 말하지 않는다. 정상 전달 구간과 드롭 구간을 분리해 해석해야 합니다.

교정된 문장: Developer v1의 최대 처리량을 500 RPS로 확정하지 않는다. 본 실험은 500 RPS까지만 관측했습니다.

안전 재사용 문장: 이번 숫자는 본 환경의 관측값이며 운영 한계나 보장값이 아닙니다.

교정 · RESULTS.md / DECISION-TREE.md

계획 대비 실행

계획: 조건별 3회 반복, request ID 대조, payload hash, 메시지 크기 검증.

실행: 대부분 한 번씩 실행했고, 결과 판정은 APIM/EH 서버 카운터와 19개 result.json의 클라이언트 성공값에 의존했습니다.

안전 재사용 문장: 결론은 방향성과 관측 사실 중심이며, 반복 분산과 end-to-end reconciliation은 별도 검증해야 합니다.

메타데이터만 기록한 기준선

N8/N64는 App Insights body 0B일 뿐이며 diagnostics disabled가 아닙니다.

집계 창 경계

A8 150,178은 측정창 경계와 warmup 잔여가 섞였을 수 있어 요청 단위 완전성 증명으로 쓰지 않습니다.

조건부 · RESULTS.md

드롭 0의 의미

APIM/EH drop 0만으로 최종 감사 무손실을 증명하지 않습니다. end-to-end reconciliation이 필요합니다.

미검증 · EXPERIMENT-SPEC.md

임계값 표현

8KB는 300 RPS 드롭 0과 400 RPS 드롭으로 전환만 관측했으며 안정 임계값은 아닙니다.

조건부 · RESULTS.md

SKU 지표 비대칭

v1은 Capacity/Duration/드롭, v2는 EH arrival 중심입니다. v2 CPU/memory 미수집으로 메커니즘은 조건부입니다.

조건부 · RESULTS.md

클라이언트 지연

단일 asyncio 부하 생성기와 TLS 영향으로 p95/p99 꼬리가 섞였습니다. APIM 판정은 서버측 지표를 우선합니다.

조건부 · EXPERIMENT-SPEC.md

공식 고부하 경고
