Lab 13 · Evidence report

APIM 로깅 성능·무손실 벤치마크

고객 관점의 결론은 단순합니다. API가 200으로 성공해도 감사 로그가 전달됐다는 뜻은 아니며, 본 관측에서는 APIM Event Hub 로거가 큐 한도에서 조용히 드롭할 수 있었습니다.

요약

API 성공 ≠ 로그 전달

19개 클라이언트 JSON은 모두 offered == successful, errors 0이지만, E8/E64에서는 APIM EventHubDroppedEvents가 관측됐습니다.

확정 · RESULTS.md + result.json

EH namespace는 병목 아님

APIM-reported drops 중에도 Event Hubs ThrottledRequests는 0으로 기록됐습니다.

확정 · EXPERIMENT-LOG.md

payload가 운영 범위를 좁힘

8KB E8은 300 RPS에서 드롭 0, 400 RPS에서 2,933 드롭이었고 64KB E64는 300 RPS에서도 41,435 드롭이었습니다.

조건부 · RESULTS.md

body 로깅은 Duration 증가

A8은 metadata-only N8 대비 APIM Duration을 높였습니다. 500 RPS에서는 N8 0.10~0.35 ms, A8 0.90~2.50 ms입니다.

확정 · EXPERIMENT-LOG.md

Basic v2 차이는 조건부

Basic v2는 관측 창에서 약 30,000/min EH 도달과 클라이언트 전부 200을 보였지만, v2 CPU/memory와 드롭 메커니즘은 미수집입니다.

조건부 · RESULTS.md

범위 주의: 원래 계획은 조건별 3회 반복과 request ID/hash reconciliation이었으나 실행 데이터는 대부분 one run per cell이며 서버 카운터 중심입니다. N은 metadata-only 기준선이지 diagnostics disabled가 아닙니다.

가설 판정

H1 · App Insights 8KB body 비용

의도 기준: A8 평균 gateway CPU 또는 p99가 N8보다 의미 있게 높고 세 반복이 같은 방향.

실제 증거: 3회 반복은 없었지만 APIM Duration은 모든 RPS에서 N8보다 A8이 높았고 500 RPS는 0.10~0.35 ms에서 0.90~2.50 ms로 증가했습니다.

판정: 방향 지지. 처리량 저하 수치는 1,000 RPS 미검증.

확정 · EXPERIMENT-LOG.md / RESULTS.md

H2 · Event Hub 8KB 500 RPS 무손실

의도 기준: generated/offered ≥ 99%, 성공 RPS ≥ 495, 오류율 ≤ 1%, p99 ≤ N8의 120%, 모든 request ID가 EH consumer에서 확인, payload hash 일치.

실제 증거: 클라이언트는 150,000/150,000 성공했지만 APIM EventHubDroppedEvents가 대량 관측됐습니다. 300 RPS 이하는 드롭 0, 400 RPS는 2,933 드롭입니다.

판정: 500 RPS 무손실은 반박. 정확한 드롭률 미확정.

확정 · RESULTS.md

H3 · Event Hub 64KB 500 RPS 무손실

의도 기준: H2와 동일하되 64KB 전체 메시지와 N64 대비 p99를 확인.

실제 증거: E64는 300 RPS에서 41,435, 500 RPS에서 76,434 EventHubDroppedEvents가 관측됐고 EH throttling은 0입니다.

판정: 64KB에서는 관측 운영 범위가 8KB보다 더 좁습니다.

확정 · EXPERIMENT-LOG.md

계획 대비 실행

계획: 조건별 3회 반복, request ID 대조, payload hash, 메시지 크기 검증.

실행: 대부분 한 번씩 실행했고, 결과 판정은 APIM/EH 서버 카운터와 19개 result.json의 클라이언트 성공값에 의존했습니다.

한계와 주의

반복 수

planned three repeats versus mostly one run. 3회 반복은 명세였지만 실행은 대부분 one run per cell입니다.

미검증 · EXPERIMENT-SPEC.md

대조 누락

missing request-ID/hash/message-size reconciliation. request ID 집합, payload hash, EH consumer 메시지 크기 대조가 완료되지 않았습니다.

미검증 · EXPERIMENT-SPEC.md

기준선 의미

metadata-only baseline: N8/N64는 App Insights body 0B일 뿐이며 diagnostics disabled가 아닙니다.

확정 · EXPERIMENT-LOG.md

집계 창

warmup contamination in App Insights counts. A8 150,178은 측정창 경계와 warmup 잔여가 섞였을 수 있습니다.

조건부 · RESULTS.md

드롭 0의 의미

drop=0 versus end-to-end losslessness: APIM/EH drop 0만으로 최종 감사 무손실을 증명하지 않습니다.

미검증 · EXPERIMENT-SPEC.md

임계값 표현

300-to-400 RPS transition versus stable threshold. 8KB는 300 RPS 드롭 0과 400 RPS 드롭으로 전환만 관측했으며 stable threshold는 아닙니다.

조건부 · RESULTS.md

SKU 지표 비대칭

asymmetric v1/v2 metrics and missing v2 CPU/memory. v1은 Capacity/Duration/드롭, v2는 EH arrival 중심입니다.

조건부 · RESULTS.md

클라이언트 지연

client p99 artifacts: 단일 asyncio 부하 생성기와 TLS 영향으로 p95/p99 꼬리가 섞였습니다.

조건부 · EXPERIMENT-SPEC.md

공식 고부하 경고

untested 1,000 RPS official warning. 본 실험은 1,000 RPS 초과 App Insights throughput 40~50% 감소 경고를 검증하지 않았습니다.

미검증 · EXPERIMENT-SPEC.md

고객 실행 안내

API와 로깅 SLO 분리

API 200 성공률과 감사 로그 전달률을 별도 SLO로 정의하십시오. Event Hub 드롭은 API 오류로 나타나지 않습니다.

확정 · RESULTS.md

드롭·싱크 동시 모니터링

APIM EventHubSuccessfulEvents/EventHubDroppedEvents와 EH IncomingMessages/ThrottledRequests를 함께 감시해 APIM 큐 문제와 EH 용량 문제를 분리하십시오.

확정 · EXPERIMENT-LOG.md

부하 모델은 bytes/sec로

peak RPS multiplied by logged payload size로 계획하십시오. 64KB는 300 RPS에서도 드롭이 발생했습니다.

확정 · RESULTS.md

SKU별 권위 지표 선택

v1은 classic Capacity를 사용하고, v2는 Capacity 대신 CPU/memory metrics를 수집하도록 테스트 계획을 바꾸십시오.

조건부 · RESULTS.md

body 크기 축소

전체 body 대신 필요한 필드, 요약, 해시, 샘플, 또는 크기 제한을 적용해 gateway logging cost를 낮추십시오.

확정 · DECISION-TREE.md

고객 환경 재시험

리전, SKU, 정책 조합, backend latency, payload 분포가 바뀌면 결과가 달라질 수 있으므로 customer environment에서 재측정하십시오.
