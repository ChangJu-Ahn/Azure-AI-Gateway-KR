1 · 결론 (TL;DR)

확정 · 핵심

EH는 8KB 초과를 무손실로 찍는다

64KB 요청: C2=8KB 잘림(App Insights 상한), C3=EH에 64KB 전량(소비로 확인). EH를 쓰는 이유를 직접 실증.

방향성 확인

용량↑ → EH 비용↑

body 8→64→200KB에서 C3 CPU 21→26→37%로 가장 가파르게 상승. C2는 8KB 상한이라 로깅 몫 평탄.

재확인

App Insights body 로깅은 CPU를 더 쓴다

포화(4×250): C2 CPU 74.5% vs C1 66.5%(+8pp). C3는 비동기라 +1pp(게이트웨이 거의 무부담).

한 줄: 성능으로 EH(C3)는 게이트웨이에 거의 부담 없음(비동기) — 단 body가 커질수록 인라인 직렬화 비용이 증가. 감사로 EH는 App Insights(8KB 잘림)와 달리 전량 무손실 — 큰 payload일수록 EH의 가치가 커진다.

그림 2 · body 크기별 게이트웨이 CPU% — C3(EH)가 가장 가파르게 상승(방향성). C2는 8KB 상한이라 로깅 몫 평탄
EH throttle/drop = 0 (전 구간): 200KB×수백 RPS는 1TU(1MB/s)를 넘겼을 것으로 추정되나 버퍼링·재시도로 유실 없이 흡수. "무손실의 대가=drop"은 더 센 부하에서만 (미도달). EH가 APIM 레이턴시에 back-pressure를 주지 않는 비동기 디커플링 가정과 정합.

6 · 공식 문서 근거 (C2 vs C3 성능 서술의 비대칭)

핵심: C2·C3를 직접 비교(head-to-head)한 공식 문서는 없다. 그러나 성능 저하 경고가 오직 C2/App Insights 문서에만 붙어 있고 C3/Event Hub는 정반대로 포지셔닝된다 — 이 서술의 비대칭 자체가 본 실측(C2 +8pp·8KB 잘림 vs C3 +1pp·무손실)과 방향이 일치한다.
근거C2 · App InsightsC3 · Event Hub
성능 경고✅ 명시: "40–50% reduction in throughput" (>1,000 rps)❌ 없음 — "millions of events/sec", "decouples"(비동기)
body 로깅"significantly decrease performance" → "skip … Body logging""not affected by sampling. All invocations logged"(무손실)
손실 / 상한샘플링 의도적 유실, body 8KB샘플링 무관 전량, 200KB
감사 적합성"not intended to be an audit system""highly scalable data ingress"(감사·오프라인 분석)
정직하게: 문서의 "−40~50% throughput"은 완전 포화(>1000rps) 전제 → 본 실험은 mock이 게이트웨이를 60-75%까지만 써서 수치(크기)는 미재현(H3). 저하 방향은 문서·실측 일치, 크기는 본 환경 미검증.

7 · 한계

  1. CPU 완전 포화(100%) 미도달: mock return-response는 게이트웨이를 60-75%까지만 사용 → 문서의 "throughput 40~50%↓"(완전 포화 전제)는 여전히 미검증(H3). 실백엔드/무거운 정책이면 포화 가능.
  2. EH throttle 미발생: 우리 부하로 1TU를 유실까지 몰지 못함(버퍼 흡수). drop은 더 센 부하 필요.
  3. EH 200KB 소비 샘플 미확보: 소비 배치 타이밍상 8192·65536만 캡처(200KB는 log-to-eventhub 200KB 상한 이내라 전송은 됨).
  4. 프로파일 B RPS 노이즈: 1엔진·소규모라 RPS 절대값 변동. CPU%가 더 안정적 지표.
