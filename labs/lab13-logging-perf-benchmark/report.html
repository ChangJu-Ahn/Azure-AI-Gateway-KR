APIM 게이트웨이에서 로깅 구성이 성능에 미치는 영향을 가설 → 실측 → 검증으로 정량 평가

1 · 결론 (TL;DR)

가설 확인

C2는 throughput를 깎는다

App Insights body 로깅 → throughput −26%, 평균 응답 +21%.

가설 확인

C3는 페널티가 없다

body를 Event Hub(비동기)로 빼면 696 RPS ≈ C1. 무손실 감사 + 성능 유지.

가설 확인

단건이 아닌 부하 현상

단건 서버측 TotalTime 0~1ms — 구성 간 구분 불가.

한 줄 결론: 무손실·대용량·샘플링 무관 감사가 필요하면 App Insights body 로깅(C2) 대신 log-to-eventhub(C3)가 옳다 — 감사 이점을 유지하면서 throughput 페널티가 없다.

2 · 실험 설계 & 가설

백엔드 지연을 원천 배제하기 위해 return-response mock(백엔드 없음)으로 크기 지정 응답을 생성하는 bench API를 대상으로, 3개 로깅 구성을 동일 조건에서 비교했다.

구성로깅 방식공식 문서 기반 가설
C1로깅 없음기준선(최소 오버헤드)
C2App Insights + 응답 body 8KB"payload 로깅 → throughput 40~50%↓(>1,000rps)"; 8KB에서 cap
C3App Insights body=0 + log-to-eventhub"샘플링 무관·전량·200KB"; 부하에서 평탄

3 · 측정 격리 방법론

  • 백엔드 제거 — return-response mock → BackendTime = null/0(데이터로 확인). "APIM이 제어 못 하는 백엔드 지연" 변수 없음.
  • 네트워크 배제 — 권위 지표는 서버측 TotalTime − BackendTime(클라이언트↔APIM 네트워크와 무관). 클라이언트 wall-clock ~1.3s vs 서버측 ~0–1ms 대비가 이를 극적으로 보여준다.
  • 중립 자(ruler) — GatewayLogs 진단은 C1/C2/C3 전 구성 상시 ON이라 그 자체 오버헤드는 delta에서 상쇄.

5 · 1차 — 단건 서버측 게이트웨이 시간

모든 구성·모든 body 크기에서 서버측 TotalTime이 0~1ms(정수 ms 해상도의 바닥). 단건 로깅 오버헤드는 마이크로초 단위로 1ms 측정 해상도 미만 → 단건으로는 관측 불가.

7 · 한계

  • 단일 티어(Standard v2, 1 unit), 엔진 1개·50 VU·~600 rps 천장 → 문서의 40~50%(>1,000 rps)와 크기 직접 비교 불가, 방향성만.
  • 실행 간 변동(매 실행 새 엔진) → C3>C1(696 vs 626)은 노이즈, 정직하게는 C3 ≈ C1.
  • 단일 body(8KB), 90초 1회. 반복·다중 body·다중 유닛으로 확장 시 정밀도↑.
