Lab 13 최종 결과 보고서 — APIM 로깅 성능·로그 전달 벤치마크

실험 결과 요약

한 줄 요약: 두 경로 모두 API 요청은 100% 성공했으나, 포화 시 App Insights는 처리시간을 늘려 로그를 보존하고 Event Hub는 로그를 폐기한다.

핵심 발견

  1. 본문 로깅은 APIM 처리시간 증가
  2. App Insights 본문 상한은 8,192 bytes. 초과 시 Event Hub 필요
  3. 평시(100~400 RPS)에는 Event Hub 경로가 게이트웨이를 더 무겁게 사용(200 RPS Capacity: N8 58% / A8 66% / E8 85%)
  4. 포화(500 RPS)에서는 역전. E8 Duration 0.4~1.7 ms < A8 0.9~2.5 ms이나 로그 폐기가 대가
  5. 드롭 주체는 Event Hubs가 아닌 APIM 게이트웨이
  6. 부하를 낮추거나 SKU를 올리면 드롭 소멸. 500 RPS는 Developer v1의 공식 예상 최대치

적용 범위: Developer v1, Korea Central, 8KB·64KB, 100~500 RPS, 대부분 1회 실행. 고객 환경 재검증 필요

검증 범위

  • 환경:
    • Azure API Management(APIM) Developer v1 SKU
    • Korea Central;
    • Basic v2는 공식 가격표에 예상 최대 RPS가 없고 포함 요청 초과분을 추가 과금하는 체계(= RPS 차이에 의해 EH Drop을 확인하기 위함)
  • 조건: 로그 저장소는 App Insights와 Event Hub. payload(요청 데이터 크기)는 8KB와 64KB, RPS는 초당 요청 수.
  • 기준선: metadata-only 기준선(N8/N64)은 App Insights 메타데이터만 기록. App Insights diagnostic을 완전히 끈 상태가 아님. 즉, body bytes만 0으로 설정.
  • 정의: 무손실은 요청 로그가 모두 도착했다는 의미이나 요청 단위 증명은 완료되지 않음. 드롭은 APIM EventHubDroppedEvents, Capacity는 classic v1 부하, Duration은 APIM 서버측 처리시간

질문 2 — 8KB를 넘는 본문은 어떻게 로깅해야 하는가

  • 가설: App Insights 진단 설정만으로는 8KB를 넘는 본문을 남길 수 없어 다른 경로가 필요하다.
  • 판정: 확인

  • 근거: 두 경로의 본문 상한

    경로본문 상한근거
    App Insights 진단 설정8,192 bytes(8KB)BodyDiagnosticSettings.bytes의 maximum: 8192
    log-to-eventhub 정책200KB, 초과분 자동 절단정책 문서 Usage notes

  • 본 실험의 적용

    • 64KB 본문(N64/E64)은 Event Hub 경로로만 측정
    • 8KB 초과 본문 감사는 사실상 Event Hub 계열만 가능

결론: 1) 8KB 초과 본문은 Event Hub 경로 필수 2) Event Hub를 함께 설계한다면, 이벤트 미처리 가능성을 전제로 설계

질문 6 — Developer v1과 Basic v2 비교에서 전달 결과가 달랐는가

저장소 선택 의사결정 흐름

로깅 목적을 먼저 정하고, 본문 필요 여부와 8KB 초과 여부로 저장소 후보를 좁힌 뒤, 드롭이 실제로 발생하는 Event Hub 경로에서 목표 부하를 검증합니다.

단계별 상세 보기(클릭해 주세요) — 각 단계의 근거와 운영 종단

  1. 1. 로깅 목적

    모니터링·진단 목적인지, 무손실 감사 목적인지 먼저 정의합니다.

    모니터링·진단이면 여기서 종료: App Insights + 적정 기록 비율 (본문 8KB 상한)

  2. 2. 본문 필요 여부

    감사 경로라면 요청·응답 본문 기록이 필요한지 확인합니다.

  3. 3. 8KB 초과 여부

    필요한 본문이 8KB 초과 여부에 해당하는지 확인합니다. 초과하면 Event Hub만 본문 저장소 후보가 되며, 200KB를 넘는 부분은 잘립니다.

  4. 4. 저장소 선택

    본문 8KB 초과는 앞서 Event Hub로 고정되어 이 분기에 오지 않습니다. 여기에 도달하는 것은 메타데이터만 또는 본문 8KB 이하이며, 본문이 필요 없어도 Event Hub는 닫히지 않습니다. 갈림은 목적지입니다 — 외부 실시간 스트리밍이면 Event Hub, Azure Monitor 통합이면 App Insights.

    • App Insights 100%

      메타데이터만 또는 본문 8KB 이하 · Azure Monitor 쿼리·알림 통합 중심 · 평시 게이트웨이 부담이 더 작음

      운영 종단: 데이터 수집 한도·일일 상한 확인 · 본 관측에서 드롭 미관측, 대신 처리시간 증가

    • Event Hub

      외부 실시간 스트리밍(SIEM·데이터레이크) 또는 본문 8KB 초과 · 200KB까지 지원 · 본문 없이 메타데이터만 보내도 선택 가능

      운영 종단: EventHubDroppedEvents 알림 필수 — 드롭이 나도 요청은 200

  5. 5. Event Hub 경로 부하 판정

    드롭은 Event Hub 경로에서만 관측됐습니다. 8KB 초과로 고정된 경우와 스트리밍 목적으로 Event Hub를 고른 경우 모두, 목표 RPS × payload에서 드롭 0을 증명해야 합니다. 8KB에서도 400 RPS에서 2,933건이 드롭됐습니다.

부하 초과 (아니오)

  1. 6. 용량 확보

    SKU·용량 상향 또는 기록 페이로드 축소로 용량을 확보합니다. Event Hubs TU 증설은 APIM 드롭의 기본 해법이 아닙니다.

  2. 7. 같은 부하로 재시험

    용량을 확보한 뒤 같은 부하로 재시험합니다.

    재시험 → 부하 판정 (드롭 0 확인 후 재판정)

부하 통과 (예)

  1. 8. Event Hub 확정

    드롭 0을 확인한 뒤 Event Hub 전달로 확정하고, EventHubDroppedEvents 알림을 상시 유지합니다.

실험 설계

실험 설계와 가설 판정

조건 정의: N8/A8/E8은 8KB 요청, N64/E64는 64KB 요청 기준입니다. N은 App Insights 본문 미기록 기준선, A는 App Insights 본문 기록, E는 Event Hub 로깅입니다.

본 실험은 APIM success/drop과 Event Hubs ingress/throttling을 함께 기록했습니다. API 성공률 차트는 로그 전달 성공률을 의미하지 않으며, 요청 ID 및 해시 대조와 워밍업 구간 처리는 한계에서 별도로 다룹니다.

측정 조건 정의

모든 조건에서 App Insights diagnostic이 sampling 100%로 켜져 있어 요청당 메타데이터 텔레메트리(URL·상태코드·duration)를 기록합니다. 조건별 차이는 App Insights body bytes와 Event Hub 로깅 유무뿐이며, N·E는 body 0입니다. 즉 N8/N64는 진단을 끈 상태가 아니라 본문만 기록하지 않는 기준선입니다.

계획 대비 실제 실행

명세(EXPERIMENT-SPEC.md)는 조건별 3회 반복(8KB 9런 + 64KB 6런 = 15런)을 계획했으나, 실제로는 조건별 대부분 1회 실행했습니다. 8KB는 5개 RPS(100~500)의 단조 추세로, 64KB는 2개 RPS로 방향을 뒷받침하지만 분산과 오차막대는 없습니다. 따라서 값은 방향·사실 판정에 사용하고 정밀 임계값으로 확대하지 않습니다.

운영 가드레일

  • SLO 분리

    API 200 성공률과 감사 로그 전달률을 별도 SLO로 관리하십시오.

  • 동시 모니터링

    Event Hubs TU 증설 전에 게이트웨이가 목표 RPS × payload를 견디는지 먼저 확인하십시오.

    리전·SKU·정책 조합이 다르면 결과가 달라지므로 고객 환경에서 재시험하십시오.
